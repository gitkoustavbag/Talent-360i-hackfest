# Talent 360 Design Language

This document records the visual language currently used by the Talent 360 Streamlit application. The shared implementation lives in `theme.py`; page-specific compositions live under `pages/`.

## Design Direction

Talent 360 is a governed talent workflow, so the interface balances two ideas:

- **Human progress:** warm, clear, encouraging language for employees.
- **Operational trust:** structured, precise visual cues for managers, reviewers, and admins.

The visual system is minimal but not flat. Color identifies audience and workflow state, while restrained motion adds energy without distracting from repeated work.

## Typography

- **Display and headings:** Space Grotesk
- **Body and controls:** DM Sans
- **Fallback:** the browser sans-serif family
- Headings use normal letter spacing and compact line-height.
- Large display typography is reserved for page titles and hero statements.
- Compact panels and workflow cards use smaller, denser headings.

Fonts are loaded in `theme.py` from Google Fonts.

## Audience Variants

Each page calls `apply_theme()` with an audience variant and renders an `audience_banner()`.

### Employee

Used by:

- Employee Request
- Employee Assessment

Tone: supportive, clear, progress-oriented.

Visual cues:

- Mint primary surfaces
- Coral progress and attention accents
- Plain-language cues such as `Show what you know`
- Focus on the next step rather than system complexity

### Manager

Used by:

- Manager Assignment
- Manager Review

Tone: structured, decision-oriented, operational.

Visual cues:

- Blue primary surfaces
- Teal action accents
- Language such as `ready assessment` and `development action`
- Stronger emphasis on readiness, calibration, and selection

### Governance

Used by:

- Reviewer Approval
- Admin Question Bank

Tone: controlled, quality-focused, accountable.

Visual cues:

- Amber review surfaces
- Blue supporting accents
- Language such as `quality bar`, `trusted question supply`, and `SME review`
- Approval actions are explicit and visually separated

### Analytics

Used by:

- Talent Dashboard

Tone: calm, evidence-led, interpretive.

Visual cues:

- Light analytical accent surface
- Metric cards and table-first layouts
- Language focused on outcomes, calibrated levels, gaps, and action

### Neutral

Used by:

- Home page
- Architecture page

Tone: explanatory and cross-workflow.

## Layout Patterns

### Page Header

Every page starts with:

- Numbered page title
- Short purpose statement
- Small coral marker above the title
- Divider below the header

### Audience Banner

Pages after the header show a compact banner containing:

- Audience icon
- Audience label
- One-line purpose
- Supporting description

The banner is generated by `audience_banner()` in `theme.py`.

### Employee Request Hero

The Employee Request page adds a larger intake composition:

- Growth-oriented hero statement
- Step counter
- Workflow progress rail
- Dark value strip explaining why the request matters
- Request form and selected employee context side by side

### Workflow Cards

The home and Architecture pages use compact colored cards with:

- A small symbolic icon
- Step number
- Short title
- One-sentence description

Cards use small radii, clear borders, and light hover elevation.

### Operational Pages

Manager, reviewer, and admin pages keep controls close to the workflow object they change. Their visual hierarchy should prioritize:

1. What is waiting for action
2. The decision or selection control
3. The primary action
4. The resulting status message

### Dashboard

The dashboard uses a metric row followed by dense tables. It favors scanning and comparison over decorative cards.

## Controls

- Primary actions use Streamlit primary buttons and inherit the audience accent.
- Secondary actions remain white with a light border.
- Select controls use white surfaces, dark text, and muted chevrons.
- Form labels always use dark ink for readability.
- Tables use a light border and rounded outer frame.
- Alerts and expanders use small rounded corners consistent with the rest of the application.

## Icons

The current UI uses compact text symbols for workflow icons because the project does not currently include an icon package. Symbols are used as visual labels rather than decoration:

- `◎` request or person
- `→` assignment or movement
- `✓` approval
- `▣` assessment
- `◈` calibration
- `✦` generation or creation
- `▤` dashboard or structured data
- `⌘` architecture or system connection

If an icon library is added later, these symbols should be replaced with accessible icon components while preserving their meaning and placement.

## Motion

Motion is intentionally restrained:

- Page headers fade upward on entry.
- Workflow cards and panels fade upward with a short stagger.
- Cards lift slightly on hover and gain a soft shadow.
- Architecture flow arrows gently nudge downward to suggest movement.
- Motion is disabled or reduced when the user has `prefers-reduced-motion` enabled.

No animation should delay access to a control or communicate information only through movement.

## Navigation

The Streamlit sidebar uses:

- Light mint background
- Dark readable labels
- Coral left marker for the active page
- Mint hover surface
- Slightly heavier active-page text

The page order represents the workflow, with Architecture last as the explanatory reference page.

## Accessibility Rules

- Maintain dark text on light surfaces.
- Do not rely on color alone for status or action meaning; use labels and icons too.
- Keep interactive controls large enough to scan and activate comfortably.
- Preserve visible focus states on inputs.
- Respect reduced-motion preferences.
- Keep descriptive text short enough to avoid crowding controls.
- Use semantic headings and accessible labels for progress regions.

## Implementation Notes

- Shared styling belongs in `theme.py`.
- Audience styling should be applied through `apply_theme("employee")`, `apply_theme("manager")`, `apply_theme("governance")`, `apply_theme("analytics")`, or `apply_theme("neutral")`.
- Reusable audience context should use `audience_banner()`.
- Page logic and workbook writes should remain separate from visual markup.
- Preserve the existing Excel-backed workflow and status contracts when extending the UI.
